# 助成金の実績報告・申請書チェック

## Purpose
申請時に約束したことと実際にやったことを、裏付けのある数字でつなぎ、審査側に「計画どおり実行した団体」と伝わる報告にする。書いていないことを足さない。

## When to use
- 実績報告書の様式（xlsx）の欄を書くことになった（欄のスクショが来ることが多い）
- 共同で申請する人が作った申請書・要望書のチェックを頼まれた
- 次の申請の記述欄を一緒に考えてほしい

## When NOT to use
- 内示後の交付申請 → josei-koufu-shinsei
- 経歴・団体実績の欄 → shinsei-keireki-writer

## Inputs
- 申請書一式（Drive で `title contains '申請書'` や受付番号で探す）：選んだ課題、解決策、プロモーション計画
- 報告様式（xlsx）、変更後の収支予算書、交付決定通知
- 収入報告書（券種ごとの枚数・金額、招待数、ステージ別）
- アンケート、記録写真、掲載記事の一覧、領収書

## Workflow（実績報告）
1. **申請書を読み、欄ごとに「申請時に書いたこと」を抜き出す。** 報告の欄は「申請時に選択した課題について達成したこと」「エンゲージメント施策」など、申請書の欄と対になっている。
2. **集めるものの一覧**（どの欄が埋まるか付き）と、数字を【　】にした下書きを先に渡す。
3. **数字は収入報告書から計算する**：
   ```python
   paid = 早割+前売+当日+U25+指定席          # 有料枚数
   total = paid + 招待                       # 来場者
   occupancy = total / (席数*回数)            # 入場率（有料だけの率も出す）
   share = {券種: 枚数/paid}                  # 券種の割合
   avg = 入場料収入 / paid                     # 平均単価
   loss = Σ(前売-割引価格)*割引枚数            # 割引で減った額
   gain = (指定席-前売)*指定席枚数              # 上乗せで増えた額
   ```
   「価格設計の戦略的運用」のような課題は、平均単価と増減の差し引きで説明すると具体的になる。
4. **計画にあったが実施が不明なものは【要確認】として一覧で聞く。** 実際にやったことだけを書く。
5. **弱く見える数字は出さない案を出す。** 数字を消しても文が成り立つように書く。
6. **貼る場所（シート名・行番号）を添えて、欄ごとにコピペできる形で渡す。** 共有が要るなら Google ドキュメントにまとめる（Drive の create_file に HTML を渡して Doc に変換 → read_file_content で読み返して確認）。
7. Excel に直接記入するときは、画像・入力規則を壊さないよう XML を直接書き換える：
   ```bash
   python3 scripts/inject.py 原本.xlsx 記入済.xlsx spec.json   # spec: {"シート名": {"C15": "本文", "E20": 470}}
   ```

## Workflow（申請書・要望書のチェック）
実際に見つかった種類の順に見る。結果は「A. 数字の誤り／B. 確認が必要／C. 誤字・表記／D. 行数超過の可能性／E. 他の資料との違い」に分け、相手にそのまま渡せる Google ドキュメントにする。
- 単位の取り違え（千円単位の欄に円の桁で入っている等。例：1000 が 100）
- 同じ数字がシート間で違う（事業費、決算額）
- 実施時期・月がシート間で違う
- 金額が空欄の支出行
- 他の資料と違う数字（来場者数、目標人数）→ どちらに揃えるかを確認する
- 同じ活動の説明が欄ごとに食い違う（対象・時間・定員）
- 日時の衝突（ワークショップと本番が同じ時刻など）
- 誤字・同音異義（務める／努める、普遍的／不変的）、**原作名と上演タイトルの混同**
- 行数の上限：字数とセル幅から行数を見積もり、超えそうな欄は字数と上限を並べて示す

## Workflow（要望書の記述欄の文案）
- 観点の違う案を複数出し、ユーザーに選んでもらってから磨く（「バランス型」を選んだ実例）。
- **費用のかかる付帯施策を勝手に足さない。** 図書カード・講師謝礼・展示・講座は不要と言われた。招待して書いてもらう、など最小の形にする。
- **誰が何をするかを主語で書く**（講師は誰か、俳優は講師かアシスタントか）。
- 用語の意味をユーザーの使い方に合わせる（「美術」はスタッフではなく舞台美術そのもの、だった）。
- 目標値はユーザーが決める。仮の数字は【　】で出し、根拠（前年比など）を添える。

## Decision rules
- 実施したか不明 → 書かずに【要確認】。
- 人数が裏付けられない（「関係者○名」など）→ 人数を外して「出演者・スタッフが」のように書く。
- 小さい絶対数（LINEの友だち数など）→ 外す案を出す。
- 来場者数 → 報告文と収支決算書の有料入場者数・招待数・入場料収入を同じ数字にする。他の書類と数字が違うときは、何を含めたか（招待・スタッフ・当日券の仮行）を揃える。
- 事務局に以前回答した内容と食い違う経費（例：「記録用で配信には使わない」と答えた撮影費を、配信にも使った）→ 計上前にユーザーに知らせる。
- 申請時と変わった点（出演者の降板、スタッフ表記）→ 報告で説明が要ると伝える。

## Quality checks
- [ ] 各欄が、申請書の対応する欄に答えているか
- [ ] 数字が収入報告書・収支決算書と一致しているか（有料／招待／収入）
- [ ] 【要確認】が残っていないか、ユーザーに確かめたか
- [ ] 字数から見て枠に収まるか。はみ出したら削る一文を指定したか
- [ ] Google ドキュメントを読み返して、全欄が入っているか

## Failure modes と Recovery（実際に起きたもの）

| 起きたこと | 対処 |
|---|---|
| 申請書の計画（稽古動画、関係者23名の発信）をそのまま実績として下書きした | 【要確認】にして聞いた。ティザー映像は実施、人数は裏付けがないので「出演者・スタッフが」に置き換えた（ユーザーの訂正） |
| LINEの友だち数（少数）を書いた | 「人数出すのやめよか」で削除。数字なしで文が通る形にした（ユーザーの訂正） |
| 来場者数が書類ごとに違った（来場リストの数え方の違い） | 収入報告書で有料・招待を分け、報告書・収支決算書・他の申請で同じ数字を使うよう伝えた |
| 文案にユーザーが望まない費用の施策が入った | 図書カード・謝礼・展示・講座を外し、招待＋公開だけのシンプルな形にした（ユーザーの訂正） |
| 表のセルに `<b>` を入れたHTMLから Doc を作ると、読み返しで `**有料 計**` と記号付きで返ってきた | 表のセル内では太字を使わない |
