# スキル化（タスクのクローズ）

目的は、次に似た依頼を受けた Claude が最初から今回の完成状態に近い判断と作業をできるようにすること。スキルを作ること自体は目的ではない。次回の品質・速度・再現性が上がらないなら「スキル化しない」と報告して終える。

## 1. 振り返る（作業ログにしない）

会話全体を読み返し、次を短く整理する。

- 最終的に何を達成したか／最初の方法から何を変えたか
- ユーザーが重視した点、ユーザーからの修正指示（「〜はいらない」「〜が先」など。恒久ルールの候補）
- 成功した方法、失敗した方法と直し方（環境のつまずきも含む）
- 次回も使える判断基準 ／ 今回だけの情報（固有名、日付、金額、パス、URL）

**このとき、閉じるタスクに未解決の問題が残っていないかも確認する。** 見つけたら最終報告の先頭に書く（直すかはユーザーに任せる）。

## 2. スキル化するか判定する

1つ以上当てはまれば候補: 同種の作業が今後もある／3ステップ以上ある／判断基準やノウハウがある／失敗して改善方法がわかった／ユーザー固有の品質基準がはっきりした／ゼロから考えると時間がかかる／コマンドやスクリプトの組み合わせに再利用価値がある。

一度きりの情報、単純な事実、一時的な数値、特定ファイル専用の処理、一般化できない偶発的な修正しか無いなら、スキル化しない。

## 3. 既存スキルとの重複を確認する

```bash
python3 scripts/list_skills.py              # 全部
python3 scripts/list_skills.py 提案 PDF     # キーワードで絞る
```

近いスキルがあれば、次の順で考える。
- 目的が同じ → 既存スキルを改善する
- 目的は同じで今回の知見が一部 → 既存スキルに追記する
- 対象・依頼のされ方が違う → 新規に分け、description で使い分けを明記する（例:「〜は○○スキルを使う」）

**同期スキル（`~/.claude/skills/synced/` 配下、manifest の source が plugin 等）は、ここで書き換えてもアカウントに戻らない。** 既存スキルを改善する場合も、改善版を新しい置き場所に作って `.skill` でアップロードしてもらう（同名なら上書き更新になる）。

## 4. 設計する

SKILL.md に最低限これを書く。各項目は Claude がそのまま実行できる粒度で。

- frontmatter: `name`（短い英小文字・ハイフン）、`description`（何をするか＋トリガーになる言い回し＋使わない場面）。使えるキーは name / description / license / allowed-tools / metadata / compatibility だけ
- Purpose（1〜2行）／When to use（依頼例）／When NOT to use（隣のスキル名）
- Inputs ／ Workflow（番号付き手順、使うコマンド）
- Decision rules（if A → B の形。ユーザーの恒久ルールはここに残す）
- Quality checks（完了前チェックリスト）
- Failure modes と Recovery（今回実際に起きたものを優先。表にすると読みやすい）

書き方:
- 固有名・日付・パス・数値は一般化する（「episode10.wav を処理」→「入力された音声ファイルを処理」）。ユーザーが恒久ルールとして指定したもの（名義、配色、順序など）は残す
- 「なぜそうするか」が判断に効く箇所には理由を1行添える
- SKILL.md は短く。長いコード・テンプレート・判断の詳細は `scripts/`・`templates/`・`references/` に分け、SKILL.md から参照する
- 今回手作業でやって間違えやすかった操作（複数ファイルの同期、チェック、変換）は、スクリプトにする価値が高い

## 5. 自己検証する

1. スクリプトは実際に動かす。今回の実ファイルで1回、**条件を少し変えた架空の入力**（わざとミスを仕込む）で1回。仕込んだミスを全部検出できるか確かめる
2. 「今回とは少し違う同種の依頼」を1つ想定し、SKILL.md だけを読んで作業できるかを読み直す。追加質問が要りそうな箇所を直す
3. 過剰適合チェック: 案件名・特定ファイル名に依存していないか／作業ログが混ざっていないか／判断条件が曖昧でないか／既存スキルと役割が重なっていないか
4. `bash scripts/package.sh <スキルのディレクトリ> <出力先>` で検証と梱包（検証エラーが出たら直してやり直す）

## 6. 保存する

置き場所は環境で決める。

| 環境 | 保存先 |
|---|---|
| クラウドのセッション（コンテナは使い捨て） | 作業中のリポジトリの `.claude/skills/<name>/` にコミット・プッシュ ＋ `.skill` を SendUserFile で送り、claude.ai のスキル設定からアップロードしてもらう |
| ユーザーの手元の Claude Code | `~/.claude/skills/<name>/`（全プロジェクト用）か、プロジェクトの `.claude/skills/<name>/` |

このセッションですぐ使えるよう `~/.claude/skills/<name>/` にもコピーしておく。

## 7. 最終報告（この形だけ、簡潔に）

- **Task closed** — 今回完了したこと（未解決の問題があれば先頭に ⚠️ で）
- **Skill decision** — 新規作成／既存Skill更新／Skill化しない（理由）
- **Skill** — 名前と保存先（リポジトリのパス、`.skill` のフルパス、アップロードが必要か）
- **Extracted knowledge** — 3〜7項目
- **Excluded** — 今回固有のため入れなかったもの
- **Next time** — 次回の同種依頼で何が自動化・高速化されるか

## つまずきやすい点

| 症状 | 対処 |
|---|---|
| 変数を使った `rm -f $DIR/*` が安全チェックで止まる | `rm -f "${DIR:?}"/*` と書く |
| `set -o pipefail` 下で `cmd | grep -q` が偽になる | grep -q が先に終わり cmd が SIGPIPE で落ちるため。`grep 文字列 >/dev/null` にする |
| `pip install` したのに import できない | `python3 -m pip install` を使う（pip が別の Python を指している） |
| 検証で unexpected key | frontmatter のキーを許可リストに合わせる |
