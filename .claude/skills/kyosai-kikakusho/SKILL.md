# 公共劇場への共催企画書

## Purpose
劇場の担当者が上司・設置者に「なぜ共催するか」を説明できる企画書を、最短で提出できる状態にする。中身の検討（内部用）と、劇場に渡す版（提出用PDF）を分ける。

## When to use
- 「来年の〇〇ホール共催に向けた企画書を作りたい」「劇場に持ち込む企画をまとめて」
- 「地方の公共劇場に喜ばれるプログラムを検討して」「共催に足る内容かチェックして」
- 「劇場に共有できる形の企画書にして」（内部の検討資料を提出版にする）

## When NOT to use
- 助成金・補助金の申請書 → josei-data-collector（根拠データ）、josei-koufu-shinsei 等
- 学校・福祉施設などへの出張WSの営業提案 → okami-business-assistant
- ワークショップ1コマの進行案 → shinkoan-maker / okami-business-assistant
- 公演チラシ・当日パンフ → kouen-pamphlet-maker 等

## Inputs
| 必須 | 劇場名とホール／希望の時期（月まで）／公演回数と会期の日数の幅／関連プログラムの希望（WS等） |
|---|---|
| あれば | 演目と原作・形式、過去の同会場の実績（予約数・来場者数・WS参加数）、過去の企画書PDF（団体概要・受賞歴の出典）、料金、講師候補、提出版に載せる連絡先 |

演目・出演者が未定でも始めてよい。未定の項目は「未定」と書いて進める。

## Workflow
1. **会場の予約ルールを最初に確認する**（`references/public-theater-criteria.md` 5章）。本番月から受付日（例：11か月前の月の初日から3日間・抽選）を計算し、曜日と休館日を python で確かめ、「今日から何日後か」を最初の返答で伝える。受付が近ければ劇場への電話確認を促す。
2. **内部用の企画書を作る**（Claude Docs が使えればドキュメント、無ければMarkdown）。章：企画概要（表）／趣旨／前回までの実績（数字）／公演計画（日程表）／参加プログラム／準備スケジュール（図）／収支の概算／広報／団体概要／リスクと劇場への確認事項。数字は実績から出す（予約枚数、予約率、1枚あたり平均単価）。
3. **劇場の評価軸を調べる**：国の指針は `references/public-theater-criteria.md` を使い、地域の文化振興計画と劇場の課題（指定管理の要領など）はその都度検索して開く。検索結果の要約ではなく、開いたページから引用する。
4. **共催チェック**：`references/check-viewpoints.md` の10観点で評価し、会場側・市民側のメリット/デメリットを書く。結論を一文で先に出す。
5. **弱点を補強する**：弱み・ふつうの観点ごとに `references/precedents.md` から事例を選び、「地域版の案／メリット／デメリット・負担」で比べる。最後に「負担を小さくする組み合わせ」と「共催の理由を強くする組み合わせ」の2つを示す。
6. **ユーザーの決定を反映する**：日程・講師・料金・演目などの修正指示ごとに、影響する箇所（概要表、日程表、本文、図、チェック表、収支）をすべて直す。
7. **提出用PDFを作る**：`templates/proposal.html` をコピーし、`{{…}}` と例文を書き換える（表紙／概要と趣旨／実施内容／劇場・地域にとっての意義・実績・広報／役割分担・相談したいこと・団体概要の5ページ）。`node scripts/topdf.js 入力.html 出力.pdf`。全ページを `pdftoppm -r 60 -png` で画像化して確認する。

## Decision rules
- 共催の理由が弱い（子ども・若者、県民の参加が「弱み」）→ 若者が上演する機会（公募・朗読劇など小さく始められる形）、事前の出張WS、公開稽古、観劇サポート回から提案する。負担の小さい案と効果の大きい案を分けて示す。
- 会期の日数を幅で指定された（例：最小4日〜最大5日）→ 2案を「内容×案」の比較表1つにまとめる。表を2つ横に並べるとA4に収まらない。
- 参加者の発表を公演の前に置く → 発表の場当たりは前日など別の時間に移し、当日は出演者の本番準備と舞台を取り合わないようにする。発表と開演の間に10分以上。開演を遅らせる提案もしてよい。
- WSは「同時に2部屋」より「舞台上で順に」を先に勧める（受付1か所・部屋代なし）。講師が出演者なら、翌日の公演と、殺陣などのけがのリスクを指摘し、内容を素振り・型などに限る。
- 観劇者やU18を無料にする料金設定 → WS収入はほぼ0として収支に入れ、「観ればWS無料」をチケットの特典として告知するよう勧める。
- 出演者がオーディションで決まる → 講師名は「予定」と書き、出演しない場合は交通・宿泊が別に要ると書く。
- 提出版から外す：自己評価（「貸館に近い」等）、内部の収支試算・減収計算、調査メモ、ユーザーが外すよう指定した会社名・連絡先・欄。収支予算書は「共催の範囲が決まりしだい提出」と書く。
- 提出版に残す：指針・地域計画との対応表、前回までの実績（予約数は「予約」と明記し来場者数と混同しない）、役割分担（劇団が担うこと／劇場にお願いしたいこと）、相談したいこと、団体概要。
- 演目名は劇団の表記（チラシ・告知）に合わせる。一般の邦題と違う場合は「原作『〇〇』をベースにした…」と分けて書く。

## Quality checks
- 会場の受付日と曜日・休館日を、本番の月から計算し直したか
- 内部版と提出版で、会期・回数・時刻・料金・定員・講師が一致しているか
- 提出版の全ページを画像で見て、表がフッターに重なっていないか
- 人名・作品名を最後に検索して、打ち間違い・異体字がないか（下の Failure modes 参照）
- 出典は実際に開いたページだけか。数字はそのページにあるものだけか
- 日付の曜日を python（`datetime`）で確認したか

## Failure modes → Recovery
- 予約受付の期限に後から気づく → Workflow 1 を必ず最初に。受付最終日なら、その日のうちに劇場へ電話するよう伝える。
- 2案の日程表を横に並べてページからはみ出す → 比較表1つに統合する。
- 表紙に別用途のチラシ画像（オーディション告知など）を使い、ぼかしても文字が透ける → 画像を使わず、CSSグラデーションで作品の色と水平線などのモチーフだけ再現する。
- 文字列を Unicode エスケープで書いて別の漢字になる（例：「辻」が「輻」）／置換で異体字が混ざる（「増」が「增」）／句点が二重になる → 編集後に人名・作品名・「。。」を検索して直す。
- 一般的な邦題で書いたら劇団の表記と違った → チラシや告知で表記を確認してから書く。
- 出典ページが404・403 → 同じ事業の別ページを探す。見つからなければその数字は書かない。
- 「共催チェック」をそのまま提出版に入れそうになる → 提出版は Decision rules の「外す／残す」で作り直す。
