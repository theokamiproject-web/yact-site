# 公演後の配信・通販の運用

## Purpose
振込払いの配信・通販で、入金の照合から発送・URL送付・催促までを、取りこぼしなく回す。

## When to use
- 通帳（記帳）の写真が送られてきた
- 「入金待ちまとめて」「発送できる人、URLを送る人をまとめて」と頼まれた
- 舞台写真やグッズをクリックポストで送る
- 配信期間中に、通販の品目を増やしたい

## When NOT to use
- グッズの企画・業者への発注 → kouen-goods
- 公演前のリマインド・キャンセル対応 → kouen-remind-yoyaku
- お客様あての文面の文体 → mail-buntai-okami（あわせて読む）

## Inputs
- 申込フォームの回答シート（アーカイブ用・写真/グッズ用）。Sheets の get_values で読む。Claude に編集権限はない前提
- 通帳の写真（日付・振込名義・金額）
- 写真の在庫数、発送済みの記録、クリックポストの画面のスクショ（追跡番号）

## Workflow

### A. 入金の照合（通帳の写真が来たら）
1. 回答シートを読み直す。**行番号は毎回いまのシートから数え直す**（テスト申込の行があると、前回伝えた番号から1行ずれる）。
2. 通帳の入金を1件ずつ、振込名義（カタカナ）・金額・日付で申込と突き合わせる。
   - 金額の作り：配信＝単価×人数、写真＝セット×単価＋バラ2枚ごとの単価＋送料
   - 名義が一部違う（名の読みが違う・省略されている）ときは、金額と申込日で対応づけ、「推定」と書く
   - チケット会社などの売上入金は、申込と混ぜずに別に書く
3. 結果を「入金確認にチェックを入れる行」として返す（シートの行番号・お名前・入金日）。チェックすると自動でURLメールが飛ぶ仕組みなので、**入金がない行は絶対に含めない**。
4. 1回の申込で2人分払われたら、該当する両方の行を挙げる。申込が重複していそうなら、2人分か重複かを本人に確認する文面を作る。
5. 本人が「振り込んだ」と言っているのに通帳に見当たらないときは、「確認しました」と書かない。記帳範囲の外かもしれないので、入金あり／なしの2つの文面を用意する。
6. ユーザーがチェックしたあと、シートを読み直して、入金済みの全行にURL送付日時が入っているか（チェック漏れがないか）を確かめる。

### B. 入金待ちのまとめ
- 未入金の人を、申込日・入金期限（申込日＋規定日数）・超過日数つきで一覧にし、未回収の合計を出す。
- ユーザーはそのまま他所に貼ることが多い。表のあとに**コピペ用のプレーンテキスト**も出す（「コピペできるかたちにして」と言われた実例あり）。
- 期限切れには、キャンセルより先に一度催促することを勧める（配信が始まった直後は入金してもらいやすい）。

### C. 発送（舞台写真・グッズ）
1. 入金済みの注文だけを対象に、**発送指示書**を作る：まず品目ごとの合計枚数（そろえる順）、次に送り先ごとの中身と枚数。
2. 在庫と照らす。**1つでも足りない品目がある注文は、まるごと保留**にする（一部だけ送らない）。保留分の「必要数−在庫＝追加印刷数」を出す。
3. クリックポストのまとめ申込CSVを作る：
   ```bash
   python3 scripts/clickpost_csv.py 宛先.csv 出力名 "舞台写真（L判）"
   ```
   宛先.csv は UTF-8 で「郵便番号,氏名,住所1,住所2,内容品」。住所1＝番地まで、住所2＝建物名。制限超え・文字コード外・郵便番号の誤りがあるとファイルを作らずに止まる。見出し行はユーザーから受け取ったテンプレートと完全一致させる。
4. 発送のお知らせは、1人1通の下書きにする（件名は共通、本文に中身と追跡番号）。追跡番号はスクショと1件ずつ照合し、一覧で見せる。
   - お詫びの一文は、実際に待たせた人にだけ入れる（申込・入金から発送までの日数で判断）
   - 公式LINEの友だち追加リンクを1行入れる
   - **ポストに入れた分だけ送る。** 保留分の下書きは送らずに残し、「発送した人の名前を教えてもらえればその分だけ送る」と伝える
5. 送料は改定されることがある（クリックポストは2026年10月に改定）。フォームやLPの送料を変える前に、日本郵便の発表で現行料金を確かめる。

### D. 通販の立ち上げ・品目の追加
1. **今あるフォームのURLを変えない。** 同じ Apps Script プロジェクトに、ページを足すスクリプトを貼って1回だけ実行する（URL・回答シート・申込時の自動メールがそのまま使える）。ひな形：`references/goods_form_apps_script.gs`
2. 送料のルールを1つに絞ってユーザーに決めてもらう（例：Tシャツを含む／含まない／予約DVDは送料込み）。
3. 在庫数がまだ分からなくても動くようにする：在庫の欄が空なら「在庫管理なし」で受け付ける。
4. 受付終了日時で自動で締め切るトリガーを入れる。
5. LPの書き換えは lp-netlify-koukai（「公開OK」をもらってから）。X・LINEの告知は下書きだけ作る（投稿・予約はしない）。

## Decision rules
- 入金が見えない → チェック行に入れない。文面は2案。
- 不足品目がある注文 → まるごと保留。部分発送しない。
- 送料 → 分かりやすさを優先し、1つのルールにまとめる案を先に出す。最終決定はユーザー。
- 1件の入金が複数の商品に当たりうる（写真代か配信代か）→ 返信で「何の代金として確認したか」を明記する。
- 遅れのお詫び → 簡潔に、発送予定日を具体的に書く。

## Quality checks
- [ ] チェック行の番号を、いまのシートで数え直したか
- [ ] チェック行に、入金が確認できない人が混じっていないか
- [ ] 入金済み＝URL送付済みになっているか（漏れの確認）
- [ ] 発送指示書の合計枚数と、送り先ごとの枚数の合計が一致するか
- [ ] CSVの件数・追跡番号の対応を1件ずつ照合したか
- [ ] お知らせメールは、発送済みの人の分だけ送ったか

## Failure modes と Recovery（実際に起きたもの）

| 起きたこと | 対処 |
|---|---|
| 伝えた行番号が1行ずれていた | テスト申込の行があった。毎回シートを読み直して番号を出す |
| 入金済みなのにチェックが漏れていた | チェック後にシートを読み直し、URL送付日時が空の入金済み行を探す |
| 在庫が足りない品目が後から分かり、発送予定が崩れた | 発送前に品目ごとの在庫を聞き、足りない注文は保留して追加印刷数を出す（ユーザーの指示で保留が増えた例あり） |
| 写真だけの送料を据え置く案を出したが、ユーザーは一律に変更した | 送料は一律の案も並べて出し、ユーザーに決めてもらう（ユーザーの訂正） |
| 在庫数が決まらずスクリプトを実行できなかった | 在庫が空なら在庫管理なしで動く形に直した（ユーザーの訂正） |
| 送信が安全判定で止められた | 迂回せず、Gmailから手で送ってもらう（gmail-shitagaki） |
